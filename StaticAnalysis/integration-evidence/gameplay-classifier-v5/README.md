## Nova descoberta: o predicado Python é um tag de classe

`IsPlayerCombatAvatar` não aparece como método/função Python definida nos streams candidatos. A busca literal limitada aos **9.705 streams decodificados** encontrou 162 entradas com a string; os 162 payloads foram verificados por hash e parseados até EOF. Nenhum code object tem esse nome/qualname, e nenhum corpo de classe usa o nome em `co_names`. A ocorrência estrutural que importa é diferente: `combat_avatar.py` passa a string para o decorador `with_tag` ao definir `PlayerCombatAvatar`.

O código estático de `gshare.decorators.with_tag` (índice MPK `36458`, SHA-256 decodificado `51f047240995dbd21b7fad4da343449ab86298b81ee436bbcdb3e41c3f0b0c4f`) mostra que seu wrapper percorre `consts.TAGS` e executa a lógica equivalente a `setattr(cls, tag, tag in args)`, preservando também tags verdadeiras herdadas. Em `combat_avatar.py` (índice `107853`, SHA-256 `11babd1e40f2036808527dc7589df652ae108cc51e3c37f0259c951a6b09dd0d`), o módulo passa `IsCombatAvatar`, `IsPlayerCombatAvatar` e `is_fps_avatar` a `with_tag` e aplica o decorador à classe `PlayerCombatAvatar`. Assim, o **tipo Python `PlayerCombatAvatar` recebe o marcador booleano `IsPlayerCombatAvatar=True`**. Esse é o corpo/implementação Python do discriminador encontrado nesta passada; não é um método C++ nem um offset nativo.

## Caminho do marcador até o owner do modelo

O fluxo estático resultante é:

1. `PlayerCombatAvatar` deriva de `CombatAvatar`; `CombatAvatar` deriva de `ClientAreaEntity`. O módulo `engine/client/ClientEntity.py` define `ClientAreaEntity` sobre `ClientEntity`, que por sua vez deriva de `common.Entity`.
2. `combat_avatar.py` aplica `Components([...combatavatarmembers.importall()])` à classe `PlayerCombatAvatar`. `combatavatarmembers/__init__.py` inclui `cimp_model` na lista normal importada. `Components` cria um `ComponentHost` para a classe e `_addComponent` adiciona classes de componente e seus métodos ao host. O módulo `cimp_model.py` (índice `61925`, SHA-256 `04bde99e6e2715d32cacce94496d4aba3f89919aae650d513a5468da1e790f4c`) define `CombatAvatarMember` sobre `ModelComponent`.
3. `CombatAvatarMember.InitAvatarModel` chama `AvatarModel(self.area, self.area.position, self.area.yaw)`. `AvatarModel.__init__(owner, position, yaw)` encaminha esses parâmetros ao superclass; `BaseModel.__init__` guarda o argumento `owner` em `self.owner`.
4. `AvatarModel.Load` (índice `143510`, SHA-256 `0a4a57f34d1c8e14e38c08f510f1787f46659e4b2928663cf526797eac8b0ed3`) consulta `self.owner.IsPlayerCombatAvatar` nos offsets de bytecode 1146 e 1348.

O caminho Python concreto é, portanto: **classe `PlayerCombatAvatar` com tag verdadeira → componente `CombatAvatarMember` → `self.area` passado como `AvatarModel.owner` → `BaseModel.owner` → consulta do predicado no `AvatarModel.Load`**. O owner fornecido ao modelo é o objeto `area` do host de entidade, não o wrapper de classe diretamente.

## Associação explícita do IEntity ao owner

Uma inspeção focada dos módulos de modelo já identificados fecha mais um elo. `MHelper.CreateModel` (índice MPK `17226`, SHA-256 decodificado `61179f1c0859d8c40097410337147629397b65987581791e8df35ad07c417de1`) chama `MObject.CreateObject('IEntity')` e retorna o objeto criado. A rotina `MHelper.LoadSkeletonAndGraph(entity, ...)` cria `MObject.CreateObject('ActorComponent')` e armazena em `entity.Skeleton` (offsets 216–260); em seguida chama `entity.Skeleton.LoadSkeletonAndGraph(...)` (272–314). `MHelper.CreateModel` passa o IEntity à rotina (712–736) e retorna esse mesmo objeto (1336–1338). `SimpleModel.Load` (índice `68957`, SHA-256 `6e6adda8eba6dfe1153301a517282472be152fe16ed16cdfc9c61bd79499f92c`) guarda esse retorno em `self.model` e, nos offsets 1484–1528, executa `self.model.owner = self.owner`; nos offsets 1538–1562 também executa `self.model.instance = self`. Para `AvatarModel`, `self.owner` é o `area` passado por `CombatAvatarMember.InitAvatarModel`, e `AvatarModel.Load` consulta esse mesmo owner. Portanto o objeto recebido pelo store de `owner` é o wrapper Python do `IEntity`, não o `ActorComponent` em `model.Skeleton`.

Isso demonstra estaticamente a relação **IEntity-wrapper → `Skeleton` ActorComponent e Python owner (`area`) → class-tag de gameplay**, e oferece a volta pelo atributo `.instance` para `SimpleModel`. O PE contém o literal refletido `IEntity.Skeleton` em RVA `0x4f779b0`; registros adjacentes incluem ponteiros candidatos a callbacks, incluindo RVA `0x58b130` (`mov [rcx],rdx; ret`) e `0x57bd70` (`mov rax,rdx; ret`). A localização e as instruções foram registradas em `12-ientity-skeleton-property-static.json`, mas a adjacência não basta para atribuir papéis exatos a esses callbacks nem para provar que o store de `entity.Skeleton` grava `ActorComponent.Parent` (campo externo `C+0x40`). Ainda não há evidência que prove que um `Parent` observado externamente identifica o IEntity-wrapper correspondente; por isso a rota inversa **Parent/ActorComponent → esse IEntity → owner** permanece aberta. Não há garantia demonstrada de que `.owner` seja um campo C++ enumerável/leitura direta; é uma atribuição de atributo através do wrapper Python.

## Não classificar armas pelo owner sozinho

`IEntity.owner` sozinho pode produzir falso positivo: em `WeaponModel.__init__`, offsets 26–34 resolvem `super().__init__(owner, position, yaw)`; a classe deriva diretamente de `SimpleModel`. `WeaponModel.Load` chama `super().Load` (offsets 324–382), que segue a MRO até `SimpleModel.Load`. A rotina comum cria o IEntity e grava nele `owner=self.owner` e `instance=self`. `WeaponModel.AttachWeaponToAvatarBack` consulta `self.owner.IsPlayerCombatAvatar` nos offsets 1216–1236. Portanto um IEntity de arma pode ter `.owner.IsPlayerCombatAvatar == True`.

Há um discriminador Python separado: `CombatAvatarMember.InitAvatarModel` armazena o retorno de `AvatarModel(self.area, ...)` em `self.model` (offsets 38–142); não há nessa rotina escrita em `self.area.model`. As declarações de classe confirmam os ramos `AvatarModel → PoseSenderModel → SimpleModel` e `WeaponModel → SimpleModel`. Como `SimpleModel.Load` grava `IEntity.instance = self`, a condição Python mais específica, quando os atributos do wrapper estão acessíveis, é `IEntity.owner.IsPlayerCombatAvatar and isinstance(IEntity.instance, AvatarModel)`; isso rejeita o ramo `WeaponModel` mesmo quando compartilha owner e inclui subclasses como `PlayerAvatarModel`. Ela não exclui, por si só, instâncias de `AvatarModel` usadas em preview. Para filtrar somente objetos em mundo, falta provar que o `Parent` visto no ponteiro externo é a mesma IEntity do modelo antes de usar seu estado `IsInWorld`.

Não há evidência aqui para a igualdade `owner.model == IEntity.instance` ou `owner.model.model == Parent`: o produtor analisado guarda o AvatarModel em `self.model` do `CombatAvatarMember`; o IEntity guarda `.instance`; não foi achado um store que estabeleça essas igualdades nem um caminho externo de leitura de `.instance`.

## Namespace demonstrado de `AvatarModel`

Não uso `co_filename` como se fosse `__module__`. No módulo produtor `cimp_model.py` (índice MPK `61925`, SHA decodificado `04bde99e6e2715d32cacce94496d4aba3f89919aae650d513a5468da1e790f4c`), o bytecode offset 198 é `IMPORT_NAME arg=32`, e `co_names[32]` é exatamente `gclient.gameplay.logic_base.models.avatar_model`; offsets 200–206 importam e armazenam `PlayerAvatarModel` e `AvatarModel` desse módulo. No módulo de definição (índice `143510`), o offset 1034 do code object `<module>` é `LOAD_CONST arg=64`; essa constante aponta ao code object `AvatarModel`, marshal offset 2936. O começo do corpo da classe executa `LOAD_NAME __name__` no offset 6 e `STORE_NAME __module__` no offset 8. Portanto a evidência de import/definição sustenta o namespace `gclient.gameplay.logic_base.models.avatar_model` para a rota observada; não sustenta o namespace sem prefixo `gameplay.logic_base.models.avatar_model`. A execução/importação não foi realizada, então o valor efetivamente vinculado a `__name__` em runtime não foi observado.

## Errata do resolvedor `STORE_ATTR`

No primeiro rascunho desta investigação, `AvatarModel.Load` nos offsets 1040 e 1114 foi interpretado erroneamente como escrita de owner. A resolução CPython 3.14 correta usa o argumento direto de `STORE_ATTR` como índice em `co_names`: offset 1040 é `position`, offset 1114 é `yaw`. A escrita `BaseModel.__init__` offset 4 é realmente `owner` porque o argumento é 0 e `co_names[0] == 'owner'`. A inspeção focada confirma também `SimpleModel.Load` offset 1528 como `owner` em `self.model`.

Os relatórios antigos não foram editados. Em [actor-classification README](../actor-classification/README.md#resultado), as alegações dos offsets 670, 830, 886, 1146 e 1348 dependem de leituras `LOAD_ATTR` e continuam compatíveis; porém [01_parse_actor_modules.py](../actor-classification/01_parse_actor_modules.py) linha 29 resolve `STORE_ATTR` com `arg >> 1`, portanto os campos `resolved_name` dos opcodes `STORE_ATTR` em `resource-code-static.json` não são confiáveis. Em [05_python_model_links.js](../gameplay/python-model-links/05_python_model_links.js), linhas 23 e 26, o mesmo shift está aplicado a `STORE_ATTR`; nomes de store desse opcode em `model-link-static.json` são inválidos e precisam ser reinterpretados por bytecode bruto. Os offsets, bytes, hashes e as leituras `LOAD_ATTR` não são afetados por essa errata. Os leitores de `camera-binding/01-decode-binding.py` e `24-decode-callers.py` resolvem stores por índice direto, sem esse erro.

## Handoff para a entidade nativa; limite externo ainda aberto

O bridge Python está demonstrado até o objeto do tipo `IEntity` e seu atributo `owner`; a ligação com uma leitura externa de `ActorComponent.Parent` ainda não está demonstrada. `Entity.init_from_dict` chama `self.area.prop._initProperty(bdict)`. `ClientEntity.__getattr__` encaminha atributos não encontrados para `self.area.prop`, e `ClientEntity.onEntityClassRegistered` passa a classe completa para `asiocore.regist_class(klass.__name__, klass)` enquanto registra descrições de propriedades. Essas chamadas são uma rota separada para o handoff de tags/classe Python e propriedade nativa.

O que falta para a rota pedida é demonstrar que `ActorComponent.Parent` em `C+0x40` aponta para o mesmo `IEntity` cujo `.owner` foi atribuído, e identificar como o wrapper nativo e seus atributos Python persistidos podem ser resolvidos pelo leitor externo. O literal refletido `IEntity.Skeleton` e callbacks adjacentes foram localizados, mas não fecham que o store do componente ajuste o campo `Parent`; nenhum `tp_dictoffset` ou offset de wrapper foi presumido. Para uma rota alternativa de tag diretamente em propriedade nativa, ainda falta a implementação/contrato de `asiocore.regist_class`, `area.prop` e `_initProperty`. A varredura ASCII do PE fixado não encontrou a string literal `IsPlayerCombatAvatar`; isso não exclui metadados codificados ou registrados por outra rota. **Não inventei offset nem declaro concluído um classificador externo.**
